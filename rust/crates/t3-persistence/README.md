# t3-persistence

Native SQLite foundation for stores. Uses bundled SQLite with FTS5 (including
contentless-delete trigrams) and JSON functions; no system SQLite dependency.

Existing databases are supported from **migration head 69**. Migrations 70–89
are incremental ports, including conditional schema repairs and data backfills.
Earlier migrations involve legacy projections, model canonicalization and the V1
to V2 event conversion; these are not implemented here. Older databases, including
published V2 previews at 53/54, are refused before changing their schema, with an
instruction to open the previous app version once. Invalid preview histories with
later migrations are also refused.

Fresh databases atomically install a baseline generated by the real TypeScript
migrations through 69, including the initial projection metadata row and the
original ledger shape, then execute 70–89 in separate transactions. This initial
bootstrap is one transaction rather than 69 historical transactions. Existing
databases never use the baseline, and every incremental migration commits its
schema, data and ledger row together. Existing timestamps and site-local names
below 55 are preserved. V2 names and missing rows through the highest recorded id
are validated; a later build's ledger tail is accepted when the known history is
complete, just as in TypeScript. Migration logging/progress events are not wired
to a server logger yet; callers receive the executed entries.
Each step acquires `BEGIN IMMEDIATE` and rechecks the highest id after acquiring
the lock, so concurrent runners skip work committed by the winner.

`Database::open` creates parent directories, configures the writer in the same
order as `Sqlite.ts`, migrates, clears planner statistics, and opens four read-only
WAL readers. Memory databases and unavailable reader pools use the writer.
Check `reader_warning()` and `checkpoint_warning()` for fallback diagnostics.
The checkpoint thread matches the 1,000-frame passive checkpoint threshold,
100ms idle catch-up, pinned-reader stop condition and 10,000-frame writer backstop.
It uses the bundled SQLite's NOOP checkpoint support.

The store layer should use:

- `Database::writer` / `reader`: owned `Send + 'static` closures on Tokio blocking
  threads; a writer closure receives `&mut rusqlite::Connection` and a reader
  closure receives `&Connection`. The entire closure keeps one connection.
  Cancelling the awaiting task does not cancel a closure already running.
- `with_writer` / `with_reader`: synchronous equivalents for an existing blocking
  context. A clone of `Database` shares the same writer and pool.
- `transaction(behavior, closure)` / `read_transaction(closure)`: scoped write or
  snapshot read transactions; errors roll back. Async callers can create a
  rusqlite transaction inside one `writer` or `reader` closure.
- `Error` / `Result`: typed SQLite, corruption, ledger, migration, ownership,
  import, synchronization and blocking-task errors; `rusqlite` is re-exported.
- `close().await`: drops a handle on a blocking thread. The last handle closes
  connections and joins the checkpoint thread. Synchronous open and final drop
  also belong on a blocking thread. Readers close before the writer so SQLite
  checkpoints the remaining WAL on the final writable close.

Connection access is **not reentrant**: a reader, writer or transaction closure
must use its supplied connection rather than call another access method on the
same `Database` (including clones). Nested calls return `Error::NestedAccess`
before acquiring any lock, for pooled readers and writer fallbacks alike. Async
helpers check before dispatching to the blocking pool. Independent concurrent
callers remain supported; do not dispatch a second caller and synchronously wait
for it while holding a connection it may need. This also applies across different
`Database` instances opening the same file; the identity guard cannot detect that.

Every closure boundary rolls back a manual transaction left open on success,
error or unwind. Commit manual transactions before returning to keep their work.
A panic is rethrown after cleanup and releasing the connection; it does not poison
the writer for subsequent callers. Already-poisoned writer locks are recovered
only after rollback succeeds. Scoped `transaction` / `read_transaction` still
commit on success and roll back on error or unwind.

`initialize_v2_database` implements the standalone V1 snapshot path: read-only
SQLite backup (including committed WAL), a scoped PID-named temp directory,
hard-link publication preserving racing winners, and dead-PID/legacy-directory
cleanup; cleanup failures are reported to stderr and startup continues.
`Database::open_v2` additionally reads the source ledger read-only and refuses
heads below 69 before publishing a destination. The standalone
`initialize_v2_database` remains a general snapshot operation and accepts older
sources. This crate does not implement lazy legacy transcript imports or upgrade snapshots below head 69; those require a
previous TypeScript version first. Backup copies the entire snapshot in one
blocking SQLite backup step; a busy/locked source returns a typed import error
for retry rather than Node's incremental backup scheduling.

The compatible `OwnershipLock::acquire(state_dir)` holds an exclusive transaction
on `server-owner.sqlite` and never deletes it. Servers hold this for their lifetime;
CLI callers set `OpenOptions::migration_owner_directory`, so only pending schema
work acquires it. Runtime-state publication, legacy-server/service detection and
lock-file replacement monitoring live in `apps/server/src/serverOwnership.ts` and
belong to the future server lifecycle crate.

Run the scoped Rust checks from `rust/` (PowerShell):

```powershell
$env:CARGO_TARGET_DIR = 'C:\Users\Administrator\t3code-rust\rust\target\agents\t3-persistence'
cargo fmt -p t3-persistence --check
cargo clippy -p t3-persistence --all-targets -- -D warnings
cargo test -p t3-persistence
```

Run the cross-implementation check from the repository root with one command
(Node with TypeScript/SQLite support, Cargo and the installed JS dependencies
are required):

```powershell
node rust/crates/t3-persistence/tools/verify-interop.ts
```

It sets the isolated Cargo target directory itself and exercises TypeScript 80 →
Rust 84 → TypeScript 89 (citations, counts and ledger), then opens a fresh Rust 89
database in TypeScript. The fresh Rust schema is checked byte for byte per object against
`rust/fixtures/database/schema.sql`; the upgraded TypeScript schema uses the
fixture exporter's outer-whitespace trim (original TypeScript statements retain
trailing indentation). Rust close must leave no nonempty WAL. `cargo test` covers every supported starting head from TypeScript-produced
SQL snapshots; the interop command is an additional check and runs real code from
both implementations. All probe databases live in scoped OS temp directories.

`node rust/crates/t3-persistence/tools/export-baseline.ts` regenerates heads 69–89
using the real TypeScript runner. `node rust/crates/t3-persistence/tools/export-baseline.ts --check`
compares every saved snapshot's schema creation order against a real TypeScript
database without rewriting snapshots. Export uses `ORDER BY rowid` to preserve
index creation order. SQL files use LF line endings while preserving intentional
lone CR bytes within search predicates. Stored schema assertions compare bytes,
including whitespace and literals.
